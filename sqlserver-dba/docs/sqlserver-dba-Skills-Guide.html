Claude Code plugin · version 0.4

sqlserver-dba: skills for a careful senior DBA

Seven Claude skills that check a busy SQL Server's health, find where its time goes, explain why the expensive statements are expensive, untangle its deadlocks down to the code and the caller behind them, verify vendor releases, prove the smallest fix, and write it up for the team or the vendor, with a reproduction kit their support engineer can run. Claude only reads production; a person deploys every change.

Read-only on production SQL Server 2017+ with Query Store No organization data in the plugin Fixes come with exact rollbacks

Overview

The skills package a method that was worked out on a busy production server running vendor applications, integrations and in-house code. They follow the order an experienced DBA uses:

  1. Measure first. Query Store, plan-cache DMVs and plan XML say where CPU, reads, timeouts and errors go, by hour, integration, object and statement.
  2. Find the few statements that matter, and name the plan operator that costs the time and the predicate that stops it seeking.
  3. Change as little as possible: a caller fix, an in-procedure hint or small rewrite, or a narrow index, and prove the results are identical.
  4. Leave a paper trail: a guarded deploy, an exact rollback, a verify script, and a write-up with diagrams that a colleague or vendor can act on.

Each skill answers one kind of question, so Claude picks the right one from how you ask. They share one core of rules and templates, and they all read your organization's site folder: your servers, policies, baseline and the list of fixes already done. Nothing about your organization ships in the plugin.

The seven skills

Every skill starts the same way: it finds your site folder, reads the profile and the ledger, and reads the safety rules once per session. Every server query it runs is SELECT-only.

sql-health-check

read-only

"How's the server doing?" · "Is anything wrong right now?" · "Compare today with last week."

A health verdict for one server, its workload against a week ago and a known-good day, and a ranked list of the savings still available.

What it checks
CPU (the engine's own meter, hour by hour), memory and its clerks, worker threads and waits for a thread, sessions by program, the availability group, tempdb, disk space and I/O latency, log backups, blocking and long requests, deadlocks, key settings, Query Store size and state.
Live rates
A 60-second sample: batch requests, transactions, compiles and recompiles, page reads and splits, lock waits, deadlocks, I/O per database file, and the top waits with the benign ones filtered out.
Workload comparison
Today from midnight to the last complete hour against the same clock hours 7 days ago and on the baseline day: CPU, reads and timeouts by hour; average cores busy; waits by category; the top 30 objects; the biggest movers in both directions.
What you get
A verdict paragraph, a week-ago / baseline / today table, each resource with a verdict, what was fixed since, ranked candidates with estimated CPU-minutes saved per day, server settings framed as the DBA's call, and an optional PDF with an hourly CPU chart.
Hands off to
Workload hotspots for "what changed", query tuning for one object, the findings report for the PDF.

sql-workload-hotspots

read-only

"Where is the CPU going?" · "What changed since the upgrade?" · "Who is running this query?" · "Why does this keep timing out?"

Works top-down – server, database, workload group, object, statement – and stops at the level that answers the question.

Steps
  1. Triage: is the box healthy right now?
  2. Where: top objects and statements by CPU, reads, timeouts and errors against a week ago.
  3. When: hour over hour, by your workload groups (integrations, products, ad hoc).
  4. What changed: per-execution regressions and new statements between two windows, ranked by extra CPU per hour.
  5. Who: the program, host, login and process that send a statement – including failing ones nobody recognizes.
  6. Failing: timeouts and errors by day and object, engine exceptions, and the data that triggers them.
Rules it keeps
Rank by recoverable CPU per day, then user impact, then risk. Check a business table before calling a rise "load growth". Group literal ad hoc SQL by query hash. Cross-check Query Store's blind spots against the plan cache.
Scripts
01 server snapshot · 02 top consumers · 03 hourly by group · 04 regressions · 08 who runs it · 09 errors and timeouts
Hands off to
Query tuning, with a request that names the statement, its query hash, windows and per-call numbers.

sql-query-tuning

read-only analysis

"Why is this procedure slow?" · "What's wrong with this plan?" · "Can we fix the vendor's procedure?"

Ends in one sentence of root cause – statement N spends X of Y CPU because operator O reads R rows of table T per execution, since predicate P can't seek index I – and the smallest change that removes that operator.

Steps
  1. Fingerprint: definition hash, modify date, SET options, signature, plan guides, local change marker.
  2. Cost by statement: which statement, which plan, since when, which waits; plan flips at the nightly recompile.
  3. Read the plan: scans on the inner side of loops, eager spools, row goals, OR joins, implicit conversions, per-row functions, spills.
  4. Understand the data: row counts, skew, placeholder values, tables that only grow.
  5. Design and prove: 2–4 variants as read-only SELECTs; rows compared both ways; CPU and reads for each.
  6. Benchmark live with a timed delta of the plan-cache counters.
  7. Package the fix for the DBA.
Fix order
Caller or configuration fix → in-procedure hint or small rewrite → narrow, prefixed index → server settings. Query Store plan forcing follows your site's policy; the default is code first, forcing only with approval.
What you get
A patch folder: exact rollback, patched copy, guarded deploy, parity test, verify script, README and a vendor note.
Scripts
05 object profile · 06 plan operators · 07 live delta benchmark · 10 implicit conversions · 11 definition fingerprint · 12 missing indexes

sql-deadlock-analysis

read-only

"We keep getting deadlocks." · "What deadlocked last night?" · "Why does this save fail with error 1205?"

Assigns every deadlock the server still remembers to a repeatable pattern, then explains each pattern twice: the root cause (which statement locks what, through which plan and index) and what is upstream (which program, host, job, schedule or change brings the two sides together). It uses the other skills for both.

Steps
  1. Rate: deadlocks since restart, split by lock type (key, page, heap, table, metadata, application), where graphs are kept, isolation settings.
  2. Collect: every graph in the system_health event files (path found automatically) or ring buffer, or a dedicated session; a bounded collector when the files only reach back hours.
  3. Cluster: patterns by the code on each side and the locked objects, with mechanism tags and catalog candidates (local, no server).
  4. History: weeks of trend per pattern from the victim statements' failed executions in Query Store, by day and by hour of day.
  5. Root cause per side, with sql-query-tuning: the definition at the line, the plan, scans, key lookups and the predicate that stops a seek; table indexes, heaps, escalations, unindexed foreign keys, triggers.
  6. Upstream, with sql-workload-hotspots: who sends each side, when, how busy that source is, what changed when the pattern started, Agent jobs and their schedules.
  7. Fix at the right owner, verify the pattern is gone (fresh graphs compared with the earlier run), write up with sql-findings-report.
Mechanisms it recognizes
17 catalog entries, among them: lock order across tables · read-then-write conversions · two sessions on one business key · key lookup vs write · scans under page locks · heaps used as queues · serializable range locks · lock escalation · mass rewrite jobs · plan flips and placeholder values · unindexed foreign keys · schema locks · parallelism · application locks · monitoring tools · transactions held open by the client · triggers inside the transaction.
Upstream signals
Same routine on both sides, sides from different application hosts, transactions opened before the current batch, autocommit off, distributed transactions, serializable clients, Agent jobs, blank program names, negative deadlock priority, bursts.
Scripts
13 probe · 14 event-file graphs · 15 ring buffer · 16 Query Store history per pattern · 17 objects · 18 Agent jobs · Collect-Deadlocks.ps1 · Analyze-Deadlocks.ps1 · a DBA-run template for a dedicated deadlock session

sql-release-verification

read-only

"The vendor upgraded last night – check it." · "Is the hot-fix working?" · "Did the upgrade overwrite our fix?" · "They upgrade on Thursday – what should we do?"

One verdict a DBA, a manager and the vendor can all act on: working as intended, working with regressions, not working, or too early to tell, with measured before → after and re-check dates.

Steps
  1. Prepare, when a release is announced: a snapshot of the definitions, a baseline of local changes, a live benchmark of the objects that matter.
  2. Scope: the deploy window and everything added, redefined or removed.
  3. Real changes: which objects have new code and which were only re-applied (snapshot diffs, or Query Store statement texts when there is no snapshot).
  4. Local changes: did our patches, indexes, permissions, signatures, forced plans and plan guides survive? Each patch is as built, a variant, reverted, changed or missing.
  5. Same output: changed logic returns the same rows, or exactly the intended difference.
  6. Cost: per statement and per object, after vs the hours before and vs the same hours a week ago; a live benchmark in the first hour.
  7. Failures: new errors, timeouts, deadlocks and lock waits, counted apart from the deploy window itself.
  8. Verdict, to-do list with owners, re-check dates, and ledger updates.
Rules it keeps
Production is the truth; release notes are claims. Never measure in the deploy hour. Compare like with like, twice. Rare events need time before they count as fixed. Local patches are never re-applied automatically.
Scripts
19 release changes · 20 schema events from the default trace · 21 definition snapshots + Compare-Definitions.ps1 · 22 local changes check · 23 same-output template · plus hotspots 04/08/09, tuning 07/11 and deadlock 13/16

sql-daily-dashboard

read-only

"Run the dashboard." · "What's bubbling up?" · "Set up a daily dashboard for our server."

One self-contained HTML page per run, built from read-only collectors in one to three minutes. It has no server connection, so it can be opened offline, mailed or archived.

On the page
A verdict naming the worst check and "look first at"; KPIs for today, a week ago and the baseline; hourly CPU with a CPU-minutes or percent-of-server switch; integrations with CPU, timeouts, errors and business throughput side by side; a group-by-hour heatmap; sortable top objects with flags; statement movers; waits.
Work board
Bubbling up → open → ready to deploy → done-watch, read from your findings ledger, with owners and CPU.
Drill-down
For each object: today vs a week ago vs baseline, the signals behind its score, its hourly shape, statements and plans, and a ready-made request to paste to Claude.
Files
Dashboard_<date>_<HHmm>.html for each run, Dashboard_latest.html for a bookmark, and the data as JSON so a page can be re-rendered without the server.

sql-findings-report

local only

"Write this up." · "Make a vendor ticket." · "Give me a PDF for my manager."

Turns findings into documents for people who weren't in the analysis: verdict first, then the numbers, then what to do.

Documents
Analysis of one problem · vendor bug ticket with an impact assessment (data, business, exposure, performance) · short vendor note for a local patch · health or week-over-week report.
Diagrams
Mermaid diagrams that show a mechanism: the hot path from caller to the expensive operator, before-and-after plan shape, a sequence for an integration or a deadlock, a trend.
Reproduction kit
Every vendor ticket and note carries one, so the vendor's level-2 support engineer can verify the problem in under an hour: a read-only script that prints the environment and data shape that decide the plan, runs the statement as shipped and with the change (actual plans included), and measures CPU, elapsed, logical and physical reads, file I/O and waits per run, plus a row-count and checksum parity check and the statement's cost in Query Store. The ticket gets numbered steps, what to expect at each, our numbers to compare against, and the plans as .sqlplan files.
Output
Markdown rendered to HTML and PDF locally with headless Edge or Chrome, checked by screenshot before it's handed over, with the kit and plans beside the PDF. Claude never sends anything itself.

Statement 3 spends 96% of the function's CPU because a clustered index scan reads ≈ 116,000 rows of Units per call, since UnitNumber = COALESCE(L.trailer, S.trailer, '') can't seek IX_UnitNumber.

6 A vendor ticket for a failing integration

Something keeps failing an UPDATE on the carrier table. Find out who sends it and write it up for the vendor.

Skills: sql-workload-hotspots (steps 5–6: who sends it, why it fails), then sql-findings-report. The cause was a data-type precedence error: COALESCE(@p bigint, column varchar) converts every existing value to bigint, so any non-numeric value fails even when the parameter is NULL. The ticket's sequence diagram:

sequenceDiagram
  participant EXT as Partner cloud service
  participant SVC as Connector service (APPHOST, login SVCUSER)
  participant DB as Production database
  EXT->>SVC: Carrier change (address, no pay-to)
  SVC->>DB: UPDATE carrier SET ..., pay_to = COALESCE(@p bigint NULL, pay_to varchar)
  DB-->>SVC: Msg 8114 varchar to bigint, statement rolled back
  Note over SVC: Address not saved, retried next cycle
  Note over DB: ≈ 4,500 failures/day, 50 successes

The impact assessment leads with the data – addresses that never get saved – rather than CPU, and the asks are specific: type the parameter to the column, set an Application Name in the connection string, and replay what failed.

For a slow plan, the ticket's "How to reproduce and verify" section does the support engineer's work for them. Claude fills repro_kit_TEMPLATE.sql, runs it first where it measured, and puts that output in the ticket so the vendor's run compares line for line. Safety model

A DBA lets Claude look at production because Claude never changes it. The skills keep that cheap to verify.

Claude may run on production

  • SELECT against DMVs, catalog views, Query Store and narrowly filtered business tables
  • Variables, CTEs, session SET options, timed waits for a delta
  • Statistics and showplan around a read-only SELECT version of a statement

Claude never runs on production

  • Any data or schema change, including temp tables and table variables filled by an insert
  • Procedure calls, Query Store configuration, plan forcing, setting changes
  • Anything that writes: it prepares the script, and a DBA runs it

Lessons built into the rules

  • Every query runs with a timeout, so a runaway read is cancelled instead of burning minutes of CPU.
  • An extended-events ring buffer is cast to a variable once; shredding it inside a CTE re-evaluates the cast per node and can cost minutes of CPU.
  • DMVs are never joined to large user tables in one query; the optimizer has no statistics for DMVs and can scan the table once per session row.
  • Data from application or session hosts comes from a read-only collector the host's admin runs. It runs for a set duration, because hosts may be on another time zone, and writes UTC timestamps.
  • A SELECT copy of an application statement is made safe before it runs: locking hints and side effects removed, a 5-second lock timeout, low deadlock priority, and the estimated plan read first.
  • Query Store rows are summed per statement before they are named. Naming hundreds of thousands of runtime rows took minutes; the same work on the aggregated rows takes seconds.
  • Text and plan lookups never run for the whole plan cache: the entries are found first through cheap columns, then only those are read.
  • Each date gets its own daylight-saving offset (a Windows time zone name and AT TIME ZONE), and windows hold whole Query Store intervals, so "the same hours a week ago" really are the same hours.
  • Query Store history is read once per target through a seekable filter (object or query hash). One query over every target read the whole store and hit its timeout.
  • Guardrails scan PowerShell scripts run with -File as well as commands, so the bundled scripts carry no write keywords, even in comments.
  • If a production guardrail hook blocks a command, Claude stops and hands that step to you. It never rewords or splits a command to get past it.

Install and set up

1. Install the plugin in Claude Code

/plugin marketplace add <path or URL of the sqlserver-dba repository>
/plugin install sqlserver-dba@sqlserver-dba

Or declare it in your Claude Code settings (extraKnownMarketplaces with a directory or git source, and enabledPlugins). Start a new session afterwards. Remove any older standalone copies of similar skills so two skills don't answer the same request.

2. Create your site folder

Ask Claude to set up the site profile, or copy core/templates/site-profile.template.md and findings-ledger.template.md into ~/.sqlserver-dba/ and fill them in.

3. Grant the reading login

  • VIEW SERVER STATE and VIEW DATABASE STATE (SQL Server 2022: VIEW SERVER PERFORMANCE STATE)
  • VIEW DEFINITION where code fingerprints are wanted
  • SHOWPLAN where estimated plans are read
  • read access to msdb (SQLAgentReaderRole) only if Agent jobs should be named in deadlock and release work
  • db_datareader only where business-table metrics are needed

4. Add a production guardrail (strongly recommended)

A Claude Code hook that blocks write keywords in any command naming a production server. The plugin doesn't ship one: use your organization's own. The bundled scripts are written to pass one.

Requirements

  • SQL Server 2017 or later with Query Store on; 2019 and 2022 give the best data. Azure SQL Managed Instance mostly works; Azure SQL Database is not supported yet.
  • Windows first: sqlcmd with integrated authentication on the machine running Claude, PowerShell 7 for the dashboard and tools, and Git Bash's awk and tr for the health check's live-rate summary.
  • For PDFs: Edge or Chrome, and internet access to load the markdown and mermaid scripts.
